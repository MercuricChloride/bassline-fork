#+title: Bassline Data Model

* Design Goals

This document describes the canonical data model for Bassline, as well
as the canonical encoding of these forms, such that values can acquire
identity.

All Bassline programs communicate and operate using this model as a
"lingua franca".

The primary goal of this is to provide a grammatical foundation that
is small, portable, and requires zero shared vocabulary between users.

That distinction is important, because this doesn't describe what
Bassline programs mean, instead it defines a small, permanently closed
set of structural kinds, the grammar, upon which all meaning lives in
arrangements of these grammatical objects that we refer to as *dialects*.

The data values are inspired by the [[https://preserves.dev/preserves.html][Preserves]] data model, with the
primary differences being: "the mark", explicit null, no embedded
values, and a lack of annotation values.

The data model is syntax free, so any syntax you can provide that
supports what we describe is fair game, with one exception: identity
of values. Values acquire identity through exactly one canonical
encoding (CE).

** What the data model includes and doesn't include

To be included in the data model, a kind must denote a meaningful
communication construction before any common vocabulary exists.

An example of this is lists. A list is expressible as vocabulary using
=<cons car cdr>=, however this requires shared vocabulary to be
meaningful. As such we only include concepts which lets our programs
be able to work with data with zero shared words.

* The Value Space

A *value* is an *atom* or a *frame*, and any *value* may additionally carry
*the mark*.

The taxonomy is split by what a value says about its constituent parts:

| stance | kinds                         | relation to constituents                                   |
|--------+-------------------------------+------------------------------------------------------------|
| none   | atoms                         | no constituents                                            |
| framed | list, dictionary, record, set | Frames constituents as a new term                          |
| fenced | any value + the mark          | Fences constituents as a program, not its literal contents |


All values form proper trees. Cycles cannot be expressed and MUST be
rejected at every boundary. Structural sharing / interning MAY exist in
memory or in non-canonical encodings so long as it is semantically
unobservable.

Frames denote a context for the meaning of their constituents as a new
term. However framing terminates at marks. When a marked value is
framed, it doesn't denote the full meaning of the term, only its
presence and an envelope.

* Atoms

** Null

An explicitly asserted absence, and NOT the default value for
something.

The model distinguishes between three epistemic states:

1. Stated value

   A non-null value is present, denotes "something"

2. Stated absence

   A null value is present, denotes something "missing"

3. Silence

   A value isn't present, denotes "nothing"

For this purpose the values, ={k: null}= and ={}=, are different
values on purpose. Implementations and intermediaries MUST NOT
conflate them: don't drop null entries, don't fill in absent
keys. Whether a consumer treats them differently is its own judgment.

** Booleans

=false= and =true=.

** Integers

Arbitrary-precision signed integers. Value equality. Never coerced to
or from doubles: =1 ≠ 1.0=.

** Doubles

IEEE-754 64 bit floating point numbers.

This is a well supported standard and is frozen in place.

NaN is canonicalized to the quiet pattern =0x7FF8000000000000= at
construction time, not at encode time, so in-memory equality and
CE-byte equality never diverge.

=-0.0= and =+0.0= are distinct values (they encode differently).

Equality is bitwise over the canonicalized representation.

Other forms of numeric values are expressible, but as
dialects. For example one may represent rational numbers as =<rat
42 54>=. But ultimately these are semantics of number systems, not
number representation, so those belong in dialects.

** Strings

Unicode text without normalization.

Well-formed UTF-8 only. Overlong encodings and surrogate code points
MUST be rejected at every decode boundary.

The kernel never normalizes. Normalization depends on a versioned
Unicode table, so two implementations can disagree about equality
depending on which table they ship. Composed and decomposed "é" are
different strings here. Readers and writers who care can normalize
themselves.

Comparison is by code point sequence, which coincides exactly with
lexicographic byte order of well-formed UTF-8.

** Symbols

Similar to strings, but denotes a spelling. The content of the symbol
isn't interesting. By making this its own data type, we prevent
things from needing to implement recognition over stringly typed
values.

A symbol is never equal to the same-spelled string. Same encoding
rules and comparison, distinct type.

** Bytestrings

A native octet sequence, gives us a binary datatype.

* Frames

While these frames can technically be used to represent each other,
they each exist for a distinct purpose.

** Lists

A sequence of values organized by position only.

** Dictionaries

An unordered set of associations from a KEY to VAL.

The KEY must be DATA: no mark anywhere within it.

VAL can be marked, however this makes the dictionary not DATA as a
whole. Lookups still work, since lookup only compares KEYS.

Duplicate KEYS are a parse error, we do not define a canonical merge.

The canonical form of a dictionary is sorted by the CE bytes of its KEYS.

We define orderedness now because order shouldn't matter for
dictionaries and we don't want anyone to depend on it. And if you do
want ordering, you want an alist or something instead.

** Records

=<head field...>=

A Record is a list-like value.

It has a HEAD which is a VALUE, and a list of FIELD VALUES, possibly
empty.

The HEAD MAY be any VALUE.  The HEAD denotes "what frames this?".  A
"degenerate" head such as null or marked values are dialect concerns,
whether or not it makes sense is not the data model's concern.

The FIELDS are always a list, and may be empty. There isn't a
distinction between optional or empty FIELDS.

** Sets

An unordered collection of unique values.

Members must be DATA, for the same reason dictionary KEYS must be:
membership is a comparison. Deduplicating marked members by their
bytes would turn byte coincidence into a semantic claim, and the
model forbids that.

A consequence: an unmarked set is always DATA.

Duplicate members are a parse error.

The canonical form of a set is sorted by the CE bytes of its members.

** Reference without a reference type

The model has no reference kind. Since values are trees compared by
structure, "reference" splits into three styles, all dialects:

1. *By inclusion.* Just include the value itself (head position is
   natural). A copy is indistinguishable from "the same thing", so a
   copy works as a reference.
2. *By digest.* A name for a value without carrying its body, IE
   =<sha256 #[...]>= over its CE bytes. The model only contributes CE
   determinism here. Hash choice, truncation, and collision
   assumptions are dialect concerns, so the choice of hash can change
   over time without touching the model.
3. *By bearer.* A marked form (e.g. the =via= family) which can denote
   to the receiver a live affordance. Identity at this rung is up to
   the interpreting side. And like any bearer form, anyone holding
   the bytes can present them, so confidentiality is a transport
   concern.

* The Mark

** What it is

The mark is a *type flag*, not a node kind and not a record tag. Any
value, atomic or compound, may carry it. A marked value is denoted
(for example) as =mark(v)=.

In a value it is one bit. In the canonical encoding it is a prefix
byte. =mark= as an operation is just how a program sets that bit.

** Semantics: negative constituency

All of our previous values allow us to denote something that is usable
immediately to the receiver based on its structure.

The mark, however, affords us a way of expressing something that
requires explicit interpretation from a receiver before being
semantically interesting. In short it gives us a way of denoting:
"This value must be interpreted locally to know what it means."

If a marked value, =mark(v)=, is within a frame, this conveys a
semantically different structure than the value =v= within the frame.

One is purely positive information, whereas the other is positive
information that we use to locally evaluate something.

The mark *negates the constituency relation* between a value and any
container:

- The enclosing value's semantics includes the marked constituent's
  *presence and form*, but never reaches its *meaning*. The envelope
  is part of the content, the letter inside is not. Framing
  terminates at the mark, on every path.
- The marked form denotes a *standalone form*: something that is not
  semantically part of this value yet, able to be offered for
  evaluation in some evaluator's world.

** Evaluation is terminal

Evaluation is totally disjoint from the data plane and exits it:

- Results NEVER re-enter the value. A relay forwards a complete
  value. A receiver who never evaluates just holds a marked value. A
  receiver who does evaluate changes its own *world*, not the message.
- There is no substitution semantics. So there is no evaluation
  order, no partially-evaluated values, no error propagation through
  trees, and no splicing question, since no context exists to splice
  into.
- Evaluation errors are events in the evaluator's world, surfaced by
  local condition machinery. A value cannot fail.
- Tree content arises from construction only. Nothing in a value was
  ever "produced by the value's own evaluation".
- The kernel ships NO evaluate/interpret operation. Evaluation is
  just what local programs do when consuming values.

** Relocatability

This realistically is more of a suggestion since we cannot enforce
this, but it's good practice.

The meaning of =mark(v)= is a function of =v= and the evaluation site
*only*, never of the enclosing tree. Marked forms can be extracted
and stored without losing meaning. A corollary: cross-form
coordination (a =<ref k>= in one payload resolving against a =<def k
v>= in another) is a dialect convention carrying no kernel promise.
Well-behaved dialects are self-contained per payload.

** Idempotency

Marking is idempotent: =mark(mark(v)) = mark(v)=. Given that the
mark is a flag and not a node kind, this is forced: the fence negates
participation in a container, and between two directly stacked marks
there is no container, so the inner fence fences against nothing.
The flag-versus-kind choice is the real decision, defended below.

Structural nesting remains meaningful: a marked value whose *form
contains* marked constituents (=mark(<defer [mark(f)]>)=) is ordinary,
because there the inner fence has real structure to fence against.
Evaluators wanting staging levels express them in their dialect
(=<stage n form>=), never by stacking.

** Operations

The operations for marks:

- =mark(v)=
  if marked? return =v=, else return a marked twin of =v=.
- =open(v)=
  if marked? return the =form= of =v=, else it's an error
- =marked?(v)= → boolean.

=mark=/=open= are total on their domains, structural, effect-free
inverses. =open= moves a use into mention-space and MUST NOT involve
any evaluator. The form returned by =open= may itself be non-Data,
since it may contain marked constituents deeper in.

** Hygiene rules

- =equal?= never auto-opens (§6).
- Pattern matchers treat marked values as opaque unless the pattern
  explicitly acknowledges the mark ("marked value whose form matches
  P" is a legal pattern; silently matching through marks is not).
- Display and inspection are mention and MAY render forms.
- *Exclusivity invariant:* affordances are born only from evaluation
  of marked forms. Substrate-level machinery (dialogue layers
  reconstituting references, etc.) keys ONLY on marks; it never
  evaluates unmarked data. When an application explicitly feeds
  unmarked data to its own evaluator, that is the application's
  deliberate act.
- Marks enter a process at exactly two auditable sites: explicit
  =mark()= calls, and decode boundaries. Untrusted input is
  quarantined by a single =data?= check right after decode.

** Why a type flag and not a record head

The most natural-looking simplification of this design is to spell the
mark as a dialect construct. IE as a record head =<mark foo>=.

We don't do this on purpose, because with a single bit the
data/program boundary stays decidable: =data?= is one check, not a
search for a magic word. The rest of the reasons are recorded here so
we don't relitigate them.

- *Minting versus spelling.* A type flag makes interpretation requests
  something only programs can mint (=mark()= calls and decode
  boundaries — both auditable). A record head makes them something
  data can spell — every construction, merge, and deserialization
  becomes an unaudited minting site.
- *Collision and undecidability.* With a magic word, the kernel cannot
  distinguish an intended mark from a coincidental spelling; some
  vocabulary will use the word innocently, indistinguishably, forever.
  Reserved words in unreserved namespaces are a named bug class:
  prototype pollution (=__proto__=).
- *This experiment already ran*, with the same word: HTML spelled its
  evaluation mark as the vocabulary item =<script>=, and the cost is
  the XSS industry. Sanitizing HTML is the problem of implementing
  =data?= over a vocabulary-keyed mark, which is near-impossible
  (mutation XSS is parser disagreement about whether something spells
  the word). Trusted Types is the DOM retrofitting =mark()=-as-API
  decades later.
- *A frame cannot declare itself not-a-frame.* Framing flows through
  records by definition. Terminating it with something like =<script
  xyz>= requires the kernel to know a word, and opens semantic leaks.

- *The Lisp exception, located.*

  =(quote x)= as a vocabulary item works fine with a singular
  evaluator. Rebol does it interestingly with most things being data by
  default, meaning it flips the "polarity" of lisp in this regard.

  But the main difference here is that when we share some data, we can
  always tell whether something is ready for us to use as is, or should
  be a program we locally run.

  A =lang= layer may freely use quote-words. The substrate serves
  strangers with no shared dialect, so the data/program boundary has
  to sit below every dialect.

Null and the mark are grammar for the same reason. Null asserts
absence at the leaf, the mark asserts program-ness on any
value. Silence cannot say "I'm telling you nothing", and a frame
cannot say "I'm not framing this" in a context-free manner.

* Data, Equality, Order

** The Data refinement

=data?(v)= ⇔ no mark occurs anywhere in =v=, transitively:

#+begin_example
data?(v) = ¬marked?(v) ∧ ∀ c ∈ constituents(v). data?(c)
#+end_example

Implementations cache this as one bit per node at construction; the
check is O(1) everywhere it is needed. =data?= is exposed as a kernel
predicate — it is also the firewall predicate ("this input contains no
interpretation requests").

** Equality

Two predicates.

=eq?(a, b)= ⇔ =CE(a) = CE(b)=. A purely syntactic comparison of the
data inside, total over all values, marked or not. This is the right
way to deep-compare mark-bearing values, IE for transcripts, caches,
and dedupe.

=equal?(a, b)= compares semantic content. Total on DATA, where it
coincides with =eq?=. Off DATA it is *undefined*, not false:
=equal?= MUST throw if either argument fails =data?=.

So two marked values are never =equal?= (the question throws), but
they may be =eq?=. Being =eq?= says they are the same bytes, not
that they mean the same thing: what a marked form means is not
something the data plane knows. Programs that want to compare marked
values by form =open= first, which makes "we chose form as our key"
an explicit decision in the program.

Notes on =equal?=:

- The domain check comes before any traversal: no short-circuiting
  on structure first, otherwise whether a comparison throws would
  depend on contents and traversal order.
- We don't define marked values as never-equal: that is the NaN
  design, and it silently breaks reflexivity and anything keyed by
  equality.
- Also rejected: "compare around the marks" (same shape, marks in
  the same positions, payloads ignored or compared). Collapsing
  distinct requests is wrong.

** Order

- Total on Data; undefined off it. (Preserves' order is total over
  all values; ours is its restriction to Data. The partiality comes
  from the mark.)
- Structure: type rank first, then intra-type. Type rank order equals
  CE tag-byte order (§7.2), so the cross-type comparison is a byte
  comparison.
- Null ranks first: absence sorts before everything. Marked values are
  unranked.
- Cross-type numerics are rank-separated: every double sorts on one
  side of every integer regardless of magnitude. This is an
  *organizational* order for canonical-form determinism, not a
  semantic order; numeric sorts use numeric comparators.
- Intra-type:
  - booleans: false < true
  - integers: numeric
  - doubles: IEEE totalOrder over canonicalized bits (sign-flip trick:
    if sign bit set, invert all 64 bits; else set the sign bit; then
    unsigned compare)
  - strings, symbols: code point order = UTF-8 byte order
  - bytestrings: lexicographic, shorter-prefix-first
  - lists: elementwise, then length (prefix sorts first)
  - dictionaries: as key-sorted association lists, lexicographic over
    (key, value) pairs, then count (prefix sorts first)
  - records: head, then fields as a list
  - sets: as sorted member lists, elementwise, then count (prefix
    sorts first)

* Canonical Encoding (CE)

** Requirements

- *Total*, including marked values. Encoding and equality are
  different questions. Mark-bearing messages still need deterministic
  bytes for signing, logging, and replay, none of which require
  =equal?=.
- *=eq?= does not imply =equal?=.* On DATA they coincide; off DATA
  =eq?= still answers while =equal?= throws. Storage layers MAY
  dedupe identical CE byte strings without making any semantic claim.
- Unique decode: prefix-free, deterministic, no trailing garbage.
- Strict canonicity at decode. Decoders MUST reject:
  - non-minimal varints
  - non-minimal integer encodings
  - ill-formed UTF-8, overlong encodings, surrogates
  - dictionary entries not in strictly ascending key-CE order
    (strictness also enforces uniqueness, one check for both)
  - set members not in strictly ascending CE order (same trick)
  - non-Data dictionary keys and set members (a mark anywhere within
    them)
  - any double encoding of NaN other than =0x7FF8000000000000=
  - a mark prefix immediately followed by another mark prefix
    (idempotency at the byte level; same family as overlong UTF-8)
  - cycles or sharing in any syntax that can express them
- Order-preserving CE (encoded byte order matching value order) is an
  explicit non-goal.
- *Domain separation lives at signature sites, not inside CE.* Keep
  the encoding pure; signers prepend context strings.

** Tag table (single source of truth)

Provisional byte assignments. Rank order = tag order for 0x00–0x0B.
The mark prefix participates in encoding but not in rank.

| tag  | kind        | payload encoding                                    |
|------+-------------+-----------------------------------------------------|
| 0x00 | null        | —                                                   |
| 0x01 | false       | —                                                   |
| 0x02 | true        | —                                                   |
| 0x03 | integer     | varint byte-length, minimal two's-complement BE     |
| 0x04 | double      | 8 bytes big-endian (NaN already canonical)          |
| 0x05 | string      | varint byte-length, UTF-8 bytes                     |
| 0x06 | symbol      | varint byte-length, UTF-8 bytes                     |
| 0x07 | bytestring  | varint byte-length, raw bytes                       |
| 0x08 | list        | varint count, element CEs                           |
| 0x09 | dictionary  | varint count, (key CE, value CE) pairs, key-sorted  |
| 0x0A | record      | head CE, varint field count, field CEs              |
| 0x0B | set         | varint count, member CEs in ascending CE order      |
| 0x0C | mark prefix | CE of the form; next byte MUST NOT be 0x0C          |

Varints: unsigned LEB128 (7 bits per byte, high bit = continuation),
minimal form required.

Integers: shortest two's-complement big-endian byte sequence. Zero is
the single byte =0x00=. A zero-length payload is rejected. For
payloads of two or more bytes: reject a leading =0x00= unless the
next byte's high bit is set, and reject a leading =0xFF= unless the
next byte's high bit is clear.

Compound framing uses *counts*, not byte lengths. Counts are simple
and stream-encodable. Subtree skipping is not needed at the CE layer:
large structures decompose via digest indirection (rung 2 of the
reference ladder), and bytestrings, the actual bulk carriers, are
length-prefixed and skippable already. This choice cannot change
after the cut without breaking identity.

* Implementation Notes (JS reference implementation)

- The reference implementation backs integers with BigInt always,
  including small ones. If integers ride =Number=, precision silently
  dies above 2^53 and =1= conflates with =1.0=. Doubles ride
  =Number=. Internal representation is free in general (fixnum fast
  paths are fine) so long as the difference is unobservable, since CE
  is the identity.
- Embedding JS natives: a JS =Number= always constructs a double,
  even when integral. A =BigInt= constructs an integer. A JS string
  constructs a string; symbols are constructed explicitly, since JS
  has no native spelling for them.
- Canonicalize NaN at construction (=Number.isNaN= → store the quiet
  pattern). Detect negative zero with =Object.is(x, -0)=.
- Nodes are immutable and frozen. Each node caches: its =data?= bit
  (computed at construction from the mark flag and children's bits),
  and optionally its CE bytes or CE length.
- Hash-consing/interning by CE bytes is permitted: semantics is
  trees, memory may share. Interned Data gets O(1) equality via
  pointer compare.
- Value-keyed maps: key by CE byte strings.
- The complete conforming core reduces to: encode canonically, compare
  bytes. The semantic order is optional tooling; an implementation
  needs zero comparison logic beyond memcmp to deliver =eq?=,
  =equal?=, and canonical form.
- Decode is where the full rejection battery (§7.1) runs. Untrusted
  input is quarantined with one =data?= check.
- Kernel API surface, complete: constructors; accessors; =data?=,
  =marked?=; =eq?=; =equal?= and order on Data; CE encode/decode;
  =mark=, =open=. There is no evaluate.

* A textual syntax

This describes /a/ textual syntax, not /the/ form of a value: it is a
non-canonical human surface. Whitespace and spelling vary, many texts
denote one value, and there is deliberately no canonical text. Identity
is recovered by parsing to a value and encoding to CE (§7).

Parsing is two levels: a tokenizer that skips whitespace and cuts the
input into tokens, and a small grammar over those tokens. That is the
whole of it.

** Tokens

Whitespace =[ \t\n\r]+= separates tokens and carries no other meaning.
A *delimiter* is whitespace or one of =[ ] { } < > ( ) : # ' | `=.
After skipping whitespace, the first character selects the token:

- =[ ] { } < > ( ) := and =#{= are structural; =`= is the mark.
- =#[= … =]= is a bytestring: hex digit pairs, inner whitespace ignored
  (=#[DE AD BE EF]=, =#[]=).
- ='= … ='= is a string; =|= … =|= is a quoted symbol. Both hold any
  scalar but the closing quote and =\=, plus the escapes =\' \\ \n \t
  \r \|= and =\u{HEX}= (which pins an exact scalar, since the model
  never normalizes).
- A digit, or a =+= / =-= immediately followed by a digit, begins a
  number.
- Anything else begins a bare symbol: a maximal run of non-delimiter
  characters.

So every character that is not whitespace or a delimiter — including
=, ; + - * / . = ! ?= — is an ordinary symbol character. Two
consequences worth stating: a symbol that must contain a delimiter is
written quoted (=|<=|=, =|a:b|=, =|has space|=); and because =:= is its
own token it always splits a symbol from what follows, so =foo: bar= and
=foo:bar= both read as the three tokens =foo : bar=, which is what lets
dictionary entries be written =key: value=.

** Grammar

The lower four productions (=Bytes=, =String=, =Symbol=, =Number=) are
the leaf tokens the tokenizer produces; the rest is the grammar over
tokens.

#+BEGIN_example
  Document := Value*

  Value    := "`"? Datum
  Datum    := Frame | Atom

  Frame    := List | Set | Record | Dict
  List     := "[" Value* "]"
  Set      := "#{" Value* "}"
  Record   := "<" Value Value* ">"   ; the first Value is the head
  Dict     := "{" Entry* "}"
  Entry    := Value ":" Value

  Atom     := Bytes | String | Number | Symbol
  Bytes    := "#[" HexByte* "]"
  String   := "'" (char | escape)* "'"
  Symbol   := bare | "|" (char | escape)* "|"
  Number   := sign? digit+                                          ; Integer
            | sign? digit+ ("." digit+)? (("e"|"E") sign? digit+)?  ; Double, must hold "." or "e"
  sign     := "+" | "-"
#+END_example

** Outside the grammar

- *Reserved spellings.* A /bare/ symbol equal to =null=, =true=,
  =false=, =NaN=, =Infinity=, or =-Infinity= denotes that value (the
  last three are doubles); any other bare run is a symbol. Quote to
  recover the symbol: =|null|=. Quoted symbols are never reclassified.
- *Number form.* A token is a number only when it opens with a digit,
  or a sign on a digit; so =-=, =->=, and =.5= are symbols while =-5=
  and =0.5= are numbers. Integer versus double is the presence of =.=
  or =e=/=E=, so =1 ≠ 1.0= and =-0.0= is writable. A number must be
  followed by a delimiter, whitespace, or end of input: a number against
  a symbol character (=1-2=, =42px=, =1.=, or =1,2= since =,= is a
  symbol character) is a syntax error, not two tokens.
- *Mark.* =`= is a single optional prefix; two in a row is a syntax
  error, mirroring CE's rejection of a doubled mark prefix (§7).
- *Semantic checks, after parse* (same status as the CE decode
  battery): dictionary keys and set members must be Data; duplicate
  dictionary keys or set members are rejected; values are trees, so no
  text may name a cycle.
- =(= and =)= are reserved with no meaning today, kept free for a
  possible future use. Currently they are a syntax error.
