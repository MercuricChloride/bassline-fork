#+title: Bassline Data Model

* Overview

This document describes the canonical data model for Bassline as well
as the rationale driving these decisions.

The goal of Bassline is to offer a way of building programs that can
meaningfully coordinate and evolve without requiring a central
authority, shared vocabulary, or shared semantics. Compared to
traditional distributed systems, this presents a unique set of
challenges that must be overcome. The primary problem being: "How can
two parties establish semantic common ground without a central
authority or schema."

The data model defines a gramatical foundation of: atomic values, how
they can be arranged to express framing, as well as an explicit way to
share values that should be used as local programs capable of
affording richer interactions.

The distinct difference is that all of these live as "positive"
contributions of information and never presume something is live.

Additionally, by making these properties of data and not part of the
contents, it lets the contents of the data focused on expressing
"dialects", or semantically rich vocabulary without inappropriate
mixing the two directly.

* Design Goals

All Bassline programs communicate and operate using this model as a
"lingua franca".

The primary goal of this is to provide a grammatical foundation that
is small, portable, and requires zero shared vocabulary between users.

That distinction is important, because this doesn't describe what
Bassline programs mean, instead it defines a small, permanently closed
set of atoms and structural kinds that can host families of meaning we
refer to as dialects.

The data values are inspired by Rebol, EDN, and [[https://preserves.dev/preserves.html][Preserves]].

The primary difference lies in the usage of "actionable" values.

The data model is syntax free, so any syntax you can provide that
supports what we describe is fair game, with one exception: identity
of values. Values acquire identity through exactly one canonical
encoding (CE).

** What the data model includes and doesn't include

To be included in the data model, a kind must denote a meaningful
communication construction before any common vocabulary exists.

An example of this is lists. A list is expressible as vocabulary using
=<cons car cdr>=, however this requires shared vocabulary to be
meaningful. As such we only include concepts which lets our programs
be able to work with data with zero shared words.

New data types are expressible without changes to the foundation. IE
things like dates, uuids, timestamps, etc are ultimately not new forms
of data, but new arrangements of data and are best expressed as custom
vocabularies because they are not very semantically different from the
underlying types we present.

* The Value Space

A *value* is either an *atom* or a *frame*.

An *atom* is a value that has no constituents.

A *frame* is a value that forms a new value by arranging it's
consituents.

Any value may be *actionable*, shifting it's meaning from "something" to
"something to do".

All values form proper trees. Cycles cannot be expressed and MUST be
rejected at process boundaries.

* Atoms

Each of these atoms are distinct types.

** Null

An explicitly asserted absence, and NOT a default value for something.

The model distinguishes between three epistemic states:

1. Stated value

   A non-null value is present, denotes "something"

2. Stated absence

   A null value is present, denotes something "missing"

3. Silence

   A value isn't present, and is thus doesn't have a denotation.
** Booleans

=false= and =true=.

** Integers

Arbitrary-precision signed integers with value equality.

** Doubles

IEEE-754 64 bit floating point numbers.

This is a well supported standard that's frozen in place.

NaN is canonicalized to the quiet pattern =0x7FF8000000000000= at
construction time so in-memory equality and CE-byte equality never
diverge.

Other forms of numeric values are expressible, but as
dialects. For example one may represent rational numbers as =<rat
42 54>=.

** Text

UTF-8 encoded text without any normalization.

** Symbols

Similar to strings, but denotes a symbol rather than contents of
something. By making this its own data type, it prevents things from
needing to implement recognition over stringly typed values.

** Bytestrings

A native hex sequence, gives us a binary datatype.

* Frames

While these frames can technically be used to represent each other,
they each exist for a distinct purpose and are considered distinct
types.

** Lists (Ordered Framing)

A sequence of values organized by position

** Records (Ordered Labeled framing)

A Record is a list-like value.

It has a HEAD which is a VALUE, and a list of FIELD VALUES, possibly
empty. The HEAD denotes the topic the fields are discussing.

** Dictionaries (Unordered Associative Framing)

An "unordered" set of association from a KEY to a VAL.

Both KEY and VAL are VALUES.

Duplicate KEY's in a dictionary is a parse error.

The canonical form of a dictionary is sorted according to the CE bytes
of it's KEYS. The first element being the shortest key, and the last
being the longest.

We define canonical "orderedness" now because order logically
shouldn't matter for dictionaries and we don't want anyone to depend
on it when they shouldn't.

** Sets (Unordered Unique framing)

An unordered collection of unique values. Duplicate values is a parse
error.

The canonical form of a set is sorted according to the CE bytes of
it's members. The first element being the shorted value, and the last
being the longest.

* Actionable Values

As we described in the start, any VALUE may be ACTIONABLE. An
actionable value allows us to denote something which should be
interpreted, and it's contents are not semantically interesting on
their own, but exist for an evaluator to use.

An actionable value is never equal to it's non-actionable counterpart
as it has a different =actionable= bit in it's descriptor, and therefore it's
canonical encoding is different.

A consequence of this is that any actionable value, may be convered to
it's non-actionable counterpart by just flipping that single bit.

The following sections give more info about actionable values:

** Why a descriptor flag and not a record head?

The most natural-looking simplification of this design is to spell out
actionable values with a dialect construct such as a record:
=<actionable foo>=.

This is intentional as it makes checking if something is data or a
program is easily determined regardless of context.

But an added benefit is that it makes speaking and instructing two
different gramatical forms that the sender can use and the receiver
can differentiate. Giving us an explicit instruction form for
messages.

It also greatly reduces the risk for XSS or similar attacks. As
evaluation has a distinct gramatical form, meaning that a custom
dialect cannot maliciously evaluate without being easily recognized as
an actionable term.

** Actionable evaluation is outside of values

Evaluation is not part of the data model, we simply have a way of
expressing values that "want" evaluation but are still values. Any
evaluation of an actionable value is totally disjoint from the value
space and exits it.

* Equality

Canonical equality is defined by bitwise equality of two values
canonical encoded forms.

* Canonical Encoding (CE)

The canonical encoding is defined for all values.

** Requirements

A good implemention of this specification must implement:

- Encoding for all values

- Equality for all values

- A valid decoder must reject:
  - non-minimal varints

  - non-minimal integer encodings

  - ill-formed UTF-8

  - Dictionaries without strictly ascending key CE order

  - Sets with duplicate membership

- A valid encoder must maintain it's output doesn't violate the above
  rules

** General Encoded Form

All encoded values begin with a 8 bit descriptor.

| actionable flag (1 bit) | type tag (7 bit) | N-bit payload |

The first bit is used to denote a value as actionable, and the last 7
bits are reserved for the type tag.

We really only need 5 bits for this, as we only have 12 different
values. But it's fine for now.

** Type Tags
*** 0x0 Error

A type tag of =0x0= indicates an encoding error and should never occur
in well encoded values. This should cause the decoder should crash.

The purpose of this is to not have null be a default value for missing
input.

*** 0x1 NULL

=0x01= indicates a null value and doesn't have a payload

*** 0x2 FALSE

=0x2= indicates the boolean value =FALSE= and doesn't have a payload.

*** 0x3 TRUE

=0x3= indicates the boolean value =TRUE= and doesn't have a payload.

*** 0x4 INTEGER

=0x4= indicates an integer value and does have a payload.

After the descriptor should be a minimal form unsigned LEB128 varint =N=
describing how many bytes long the integer payload is.

The integer value itself should be encoded as the shortest
two's complement big endian integer with length =N=.

*** 0x5 double

=0x5= indicates a 8 byte two's complement big endian float. It should
read the next 8 bytes directly.

*** 0x6 string

=0x6= indicates a string. It should include a length varint, followed by
the payload of UTF-8 encoded bytes

*** 0x7 symbol

=0x7= is a symbol and should handle identical to string

*** 0x8 bytestring

=0x8= indicates a bytestring, and should have a length varint, followed
by a payload of raw bytes.

*** 0x9 list

=0x9= indicates a list, and should have a byte length varint, followed
by a payload of it's encoded elements.

*** 0xa dictionary

=0xa= indicates a list, and should have a byte length varint, followed
by a payload alternating [key element].

*** 0xb record

=0xb= indicates a record, and should have a byte length varint, followed
by a payload where the first value is the head, and the remaining are
the fields.

*** 0xc set

=0xc= indicates a set, and should be a byte length varint followed by
a payload of it's encoded unique elements.

** Tokens

Whitespace =[ \t\n\r\,]+= separates tokens and carries no other meaning.
A *delimiter* is whitespace or one of =[ ] { } < > ( ) : # ' " `=.
After skipping whitespace, the first character selects the token:

- =[ ] { } < > ( ) := and =#{= are structural

-  =`= is to prefix a value and denote it as actionable

- =#[= … =]= is a bytestring: hex digit pairs, inner whitespace ignored
  (=#[DE AD BE EF]=, =#[]=).

- =" ... "= is a string and =' ... '= is a quoted symbol. Both hold any
  scalar but the closing quote and =\=; the escapes are =\" \\ \n \t \r=
  in a string and =\' \\ \n \t \r= in a symbol.

- A digit, or a =+= / =-= immediately followed by a digit, begins a
  number.

- Anything else begins a bare symbol: a maximal run of non-delimiter
  characters.

So every character that is not whitespace or a delimiter including
=; + - * / . = ! ? |= is an ordinary symbol character.

A symbol that must contain a delimiter is written in it's quoted form
quoted ='a:b' 'has space'= and because =:= is its own token it always
splits a symbol from what follows, so =foo: bar= and =foo:bar= both read
as the three tokens =foo : bar=, which is what lets dictionary entries
be written =key: value=.

** Grammar

The lower four productions (=Bytes=, =String=, =Symbol=, =Number=) are
the leaf tokens the tokenizer produces; the rest is the grammar over
tokens.

#+BEGIN_example
  Document := Value*

  Value    := "`"? Datum
  Datum    := Frame | Atom

  Frame    := List | Set | Record | Dict
  List     := "[" Value* "]"
  Set      := "#{" Value* "}"
  Record   := "<" Value Value* ">"   ; the first Value is the head
  Dict     := "{" Entry* "}"
  Entry    := Value ":" Value

  Atom     := Bytes | String | Number | Symbol
  Bytes    := "#[" HexByte* "]"
  String   := '"' (char | escape)* '"'
  Symbol   := bare | "'" (char | escape)* "'"
  Number   := sign? digit+                                          ; Integer
            | sign? digit+ ("." digit+)? (("e"|"E") sign? digit+)?  ; Double, must hold "." or "e"
  sign     := "+" | "-"
#+END_example

** Outside the grammar

*** Reserved spellings
A bare symbol equal to =nil=, =true=, =false=, =NaN=, =Infinity=, or =-Infinity=
denotes that value (the last 4 are doubles); any other bare run is a
symbol. Quote to recover the symbol: ='null'=. Quoted symbols are never
reclassified.

*** Number form
A token is a number only when it opens with a digit, or a sign on a
digit; so =-=, =->=, and =.5= are symbols while =-5= and =0.5= are
numbers. Integer versus double is the presence of =.= or =e=/=E=, so =1 ≠
1.0= and =-0.0= is writable. A number must be followed by a delimiter,
whitespace, or end of input: a number against a symbol character (=1-2=,
=42px=, or =1.=) is a syntax error, not two tokens.
