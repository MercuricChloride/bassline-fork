#+title: Bassline Data Model

* Overview
This document describes the canonical data model for Bassline as well
as the rationale driving these decisions.

The goal of Bassline is to offer a way of building programs that can
meaningfully coordinate and evolve without requiring a central
authority, shared vocabulary, or shared semantics. The data model provides
a floor for this goal by defining the utterances two parties can share
before any common ground exists.

The data model defines a grammatical foundation of: atomic values, how
they can be arranged to express framing, as well as an explicit way to
share values that should be used as local programs capable of
affording richer interactions.

The distinct difference is that all of these live as "positive"
contributions of information and never presume something is live.

Additionally, by making these properties of data and not part of the
contents, it lets the contents of the data focus on expressing
"dialects", semantically rich vocabulary, without inappropriately
mixing the two.


* Design Goals

All Bassline programs communicate and operate using this model as a
"lingua franca".

The primary goal of this is to provide a grammatical foundation that
is small, portable, and requires zero shared vocabulary between users.

That distinction is important, because this doesn't describe what
Bassline programs mean, instead it defines a small, permanently closed
set of atoms and structural kinds that can host families of meaning we
refer to as dialects.

The data values are inspired by Rebol, EDN, and [[https://preserves.dev/preserves.html][Preserves]].

The primary difference lies in the usage of "actionable" values.

The data model is syntax free, so any syntax you can provide that
supports what we describe is fair game, with one exception: identity
of values. Values acquire identity through exactly one canonical
encoding (CE).


** What the data model includes and doesn't include

To be included in the data model, a kind must denote a meaningful
communication construction before any common vocabulary exists.

An example of this is lists. A list is expressible as vocabulary using
=(cons car cdr)=, however this requires shared vocabulary to be
meaningful. As such we only include concepts which let our programs
work with data with zero shared words.

The test we apply to each atom is: what can a receiver with no
vocabulary do with it? Nil denotes absence, integers denote a count, strings
denote text, symbols denote a name, bytestrings denote some raw payload.

If a kind doesn't license some use for a vocabulary-free receiver,
it's vocabulary and belongs to a dialect.

Domain specific data types are expressible without changes to the foundation.
Things like dates, uuids, timestamps, etc are ultimately not new forms
of data, but new arrangements of data, and are best expressed as
custom vocabularies.

Two kinds that other formats include and we deliberately leave out:

- Booleans. A bare =true= means nothing without the question it
  answers, and the question is always vocabulary. Dialects that want
  polarity can use symbols, or presence in a set of flags. Erlang and
  older Lisps take the same position: =true= and =false= are ordinary
  symbols there.

- Non-integer numbers.
  This is partly driven by pragmatics because having support for
  non-integers numbers for canonical representation invites a hydra
  of related issues we can avoid by just omitting them while providing
  greater freedom to users.

  Numbers that have extra information other than a literal count
  should be expressed as vocabulary. For example =(dec 15 -1)=
  for 15 x 10^-1 or a rational number as =(rat 42 54)=.


* The Value Space

A *value* is either an *atom* or a *frame*.

An *atom* is a value that has no value constituents.

A *frame* is a value that forms a new value by arranging its
constituents.

Any value may be *actionable*, shifting its meaning from "something" to
"something to do".

All values form proper trees. Cycles cannot be expressed and MUST be
rejected at process boundaries.

Note that atoms have internal structure at the representation level, but
atomhood is about the value space. That is to say an atom has no constituents that
are themselves values.

** Atoms

Each of these atoms is a distinct type.

*** Nil

An explicitly asserted absence, and NOT a default value for something.

The model distinguishes between three epistemic states:

1. Stated value

   A non-nil value is present, denotes "something"

2. Stated absence

   A nil value is present, denotes something "missing"

3. Silence

   A value isn't present, and thus doesn't have a denotation.


*** Integers

Arbitrary-precision signed integers with value equality.

The regex for this is =/^(0|-?[1-9][0-9]*)$/=

Their canonical form is a string of numeric ascii characters no leading zeros.
There is exactly one spelling of every integer anywhere in the system.


*** Text

Well formed UTF-8 encoded text without any normalization.


*** Symbols

Similar to strings, but denotes a symbol rather than contents to show.
By making this its own data type, it prevents things from needing to implement
recognition over stringly typed values.


*** Bytestrings

A sequence of raw bytes, gives us a binary datatype.


** Frames

While these frames can technically be used to represent each other,
they each exist for a distinct purpose and are considered distinct
types.


*** Lists (Ordered Framing)

A sequence of values organized by position.


*** Records (Ordered Labeled framing)

A Record is a list-like value.

It has a HEAD which is a VALUE, and a list of FIELD VALUES, possibly
empty. The HEAD denotes the topic the fields are discussing.


*** Dictionaries (Unordered Associative Framing)

An "unordered" set of associations from a KEY to a VAL. Both KEY and VAL
are values.

I use quotes around "unordered" because the order of a dictionary is meaningless
aside from the canonical identity of the dictionary.

The canonical form of a dictionary is sorted lexicographically by the
CE bytes of its keys.

Duplicate KEYs or non-ascending keys in a dictionary is a decoding error.


*** Sets (Unordered Unique framing)

An "unordered" collection of unique values. Duplicate values is a parse
error.

The canonical form of a set is sorted lexicographically by the CE bytes of
its members, with the same caveat as dictionaries.


* Actionable Values

As we described in the start, any VALUE may be ACTIONABLE. An
actionable value allows us to denote something which should be
interpreted, and its contents are not semantically interesting on
their own, but exist for an evaluator to use.

An actionable value is never equal to its non-actionable counterpart
as it has a different =actionable= bit in its header.

A consequence of this is that any actionable value may be converted to
its non-actionable counterpart by just flipping that single bit.

The following sections give more info about actionable values:

** Why a header flag and not a record head?

The most natural-looking simplification of this design is to spell out
actionable values with a vocabulary construct such as a record:
=(actionable foo)=, but we reject this notion.

This is intentional as it makes checking if something is data or a
program easily determined regardless of context with zero
vocabulary.

An added benefit is that it makes speaking and instructing two
different grammatical forms that the sender can use and the receiver
can differentiate. Giving us an explicit instruction form for
messages.


** Actionable evaluation is outside of values

Evaluation is not part of the data model, we simply have a way of
expressing values that "want" evaluation but are still values. Any
evaluation of an actionable value is totally disjoint from the value
space and exits it.


* Equality

Canonical equality is defined by bitwise equality of two values'
canonically encoded forms.


* Canonical Encoding (CE)

The canonical encoding is defined for all values.

** The header

Every value begins with a single header byte:

| tag (4 bits) | actionable flag (1 bit) | length (3 bits) |

The first 4 bits carry the type tag. The fifth bit is the actionable
flag. The last three bits carry the payload length for scalars, and
must be zero everywhere else.

| tag     | kind      | body                    |
|---------+-----------+-------------------------|
| =0x0=     | (invalid) |                         |
| =0x1=     | null      | none                    |
| =0x2=     | integer   | decimal digits (UTF-8)  |
| =0x3=     | string    | UTF-8                   |
| =0x4=     | symbol    | UTF-8                   |
| =0x5=     | bytes     | raw bytes               |
| =0x6=     | list      | values, then END        |
| =0x7=     | record    | values, then END        |
| =0x8=     | dict      | values, then END        |
| =0x9=     | set       | values, then END        |
| =0xa=     | END       | (only as the byte =0xA0=) |
| =0xb=-=0xf= | (invalid) |                         |

A header with tag =0x0= is invalid and the decoder must crash. The
purpose of this is that zeroed memory never decodes as a value, and in
particular never as null.


** Scalar lengths

Scalars (tags =0x2= through =0x5=) state their payload length in bytes.

The length is encoded as a big-endian uint in 4 different sizes.

The size of the length is tiered as follows

| payload length      | tier   | length-repr |
|---------------------+--------+-------------|
| 7 > len >= 0        | small  | uint3       |
| 255 > len >= 7      | medium | uint8       |
| 2^32 > len >= 255   | large  | uint32      |

Each form is mandatory in its range and an encoder must use the
smallest form that fits. Decoders must reject the others such that
every length has exactly one spelling.

The four-byte ceiling capable of delimiting a scalar payload is
deliberate. This gives us a maximum size of 4.3GB and realistically
nothing should ever approach this limit. This was just chosen so we
can include scalars that fit reasonable file sizes atomically, since
modern files routinely are much larger than ~16KB, and it's tedious to
be required to chunk anything over 16K.

If you have some giant dataset it should be expressed as a vocabulary
of these atoms. For example as a list of block bytestrings or
something similar, or a manifest of hashes of individual chunks.

Receivers are likely to impose much smaller limits at their boundaries
for what is a "reasonable size", but in theory the data model is
capable of expressing numbers as large as 4.3GB of raw data. 🤷

Null has no payload and its length bits must be zero.


*** Small payload

Small payloads under 7 bytes have their length stored in the last 3
bits of the header byte.

So the header + payload would be:

#+BEGIN_EXAMPLE
        mark
  ╔════╦╩╦═══╗   ╔════════════════╗
  ║tttt║m║lll║   ║payload         ║
  ╚═╦══╩═╩═╦═╝   ╚════════════════╝
   tag   length
#+END_EXAMPLE


*** Medium payload

Medium payloads under 255 bytes have their header length bits set to 7.

They are then followed by a byte specifying their length.

So the header, length, payload would be:

#+BEGIN_EXAMPLE
       mark
  ╔════╦╩╦═══╗ ╔════════╗ ╔═══════╗
  ║tttt║m║lll║ ║LLLLLLLL║ ║payload║
  ╚═╦══╩═╩═╦═╝ ╚═══╦════╝ ╚═══════╝
    tag            ╚╸length
#+END_EXAMPLE


*** Large payload

Large payloads occupy the 4 bytes following the header with length bits
set to 7 and the trailing byte set to 255.

So the header, length, payload would be:

#+BEGIN_EXAMPLE
                          4x
  ╔════╦═╦═══╗ ╔════════╗ ╔════════╗ ╔═══════╗
  ║tttt║m║111║ ║11111111║ ║LLLLLLLL║ ║payload║
  ╚════╩═╩═══╝ ╚════════╝ ╚════════╝ ╚═══════╝
#+END_EXAMPLE


** Integer payloads

The integer payload is its decimal notation as UTF-8 / ASCII: an optional
=-=, then digits with no leading zero. Zero is =0= and there is no
=-0= and no =+=. This is the same spelling the textual syntax uses,
so there is one integer notation in the whole system, and encoding an
integer is just writing it down.


** Frames

A frame's header carries no length; its length bits must be zero. Its
constituents follow, each self-delimiting, and the frame is closed by
the single byte =0xA0= (END).

A frame's extent is derivable from its constituents, so also stating
it up front would be information that could disagree with the
contents. Terminating instead means there is nothing to
cross-validate. This mirrors the textual syntax exactly: the header
byte is the open bracket, END is the close bracket.

- A record must contain at least one value (its head).
- A dictionary's constituents alternate key, value. Keys must be
  unique and in strictly ascending CE byte order.
- A set's members must be unique and in strictly ascending CE byte
  order.
- END is a single exact byte =0xA0=
- =0xA1= through =0xAF= is invalid as END carries no flag and no length.


** What a decoder must reject

- a header with tag =0x0=, or =0xb= through =0xf=
- =0xA1= through =0xAF=
- END at the top level; end of input inside a frame or a payload
- null with nonzero length bits; a frame header with nonzero length
  bits
- a length in a longer form than its value requires
- an integer payload that isn't canonical decimal notation
- ill-formed UTF-8 in a string or symbol
- a record with no head
- dictionary keys or set members out of order or duplicated
- nesting past the decoder's depth limit (implementations should have
  one)

This describes a textual syntax for working with this encoding.


** Tokens

Whitespace =[ \t\n\r\,]+= separates tokens and carries no other meaning.
A *delimiter* is whitespace or one of =[ ] { } ( ) : # ' " ` ;=.
After skipping whitespace, the first character selects the token:

- =[ ] { } ( ) := and =#{= are structural

-  =`= is to prefix a value and denote it as actionable. The mark must
  immediately prefix its value: a repeated mark, or a mark separated
  from its value, is a syntax error.

- =;= begins a comment that runs to the end of the line. A comment is
  whitespace: it separates tokens and never reaches the value space.
  There is no annotation plane — a durable note is data, e.g. a
  =(comment ...)= record in a dialect.

- =#[= … =]= is a bytestring: hex digit pairs, inner whitespace ignored
  (=#[DE AD BE EF]=, =#[]=).

- =" ... "= is a string and =' ... '= is a quoted symbol. Both hold any
  scalar but the closing quote and =\=; the escapes are =\" \\ \n \t \r=
  in a string and =\' \\ \n \t \r= in a symbol.

- A digit, or a =-= immediately followed by a digit, begins a
  number.

- Anything else begins a bare symbol: a maximal run of non-delimiter
  characters.

So every character that is not whitespace or a delimiter including
=< > ; + - * / . = ! ? |= is an ordinary symbol character (so =-> <- <=
>== read as symbols).

A symbol that must contain a delimiter is written in its quoted form
='a:b' 'has space'= and because =:= is its own token it always
splits a symbol from what follows, so =foo: bar= and =foo:bar= both read
as the three tokens =foo : bar=, which is what lets dictionary entries
be written =key: value=.


** Grammar

The lower four productions (=Bytes=, =String=, =Symbol=, =Number=) are
the leaf tokens the tokenizer produces; the rest is the grammar over
tokens.

#+BEGIN_example
  Document := Value*

  Value    := "`"? Datum
  Datum    := Frame | Atom

  Frame    := List | Set | Record | Dict
  List     := "[" Value* "]"
  Set      := "#{" Value* "}"
  Record   := "(" Value Value* ")"   ; the first Value is the head
  Dict     := "{" Entry* "}"
  Entry    := Value ":" Value

  Atom     := Bytes | String | Number | Symbol
  Bytes    := "#[" HexByte* "]"
  String   := '"' (char | escape)* '"'
  Symbol   := bare | "'" (char | escape)* "'"
  Number   := "-"? digit+          ; Integer
#+END_example


** Outside the grammar


*** Reserved spelling for nil

A bare symbol equal to =nil= denotes nil; any other bare run is a
symbol. To use nil as a symbol, it must be quoted: ='nil'=.


*** Number form
:PROPERTIES:
:ID:       35E8A819-9893-49E4-85C5-2F5EDE6F3911
:END:

A token is a number only when it opens with a digit, or a =-= on a
digit; so =-= and =->= are symbols while =-5= is a number. There is no
=+= sign for numbers meaning that =+5= is an ordinary symbol. A number
must be followed by a delimiter, whitespace, or end of input: a number
against a symbol character (=1-2=, =42px=, or =1.=) is a syntax error,
not two tokens. There are no decimal literals: =1.5= is a syntax
error, not a value!
